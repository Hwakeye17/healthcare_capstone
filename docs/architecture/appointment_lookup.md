
# Appointment Lookup Tool

## 1. Purpose

The appointment lookup tool provides deterministic, read-only access to the synthetic appointment dataset used by the Practo Support Agent.

It allows the Lookup Agent to retrieve administrative details associated with an appointment record ID. The tool also calculates an administrative prioritization score using the appointment's follow-up flag and the number of days since the record was created.

The tool is designed to support appointment-related queries without requiring an LLM to interpret or calculate structured appointment data.

## 2. Dataset

The tool reads appointment records from:

`data/generated/appointments.json`

The dataset is generated by the project's `dataset.py` script and contains 50 synthetic appointment records.

Each record contains the following fields:

| Field | Description |
|---|---|
| `record_id` | Unique appointment identifier |
| `category` | Appointment category |
| `status` | Current appointment status |
| `consultation_fee_inr` | Consultation fee in INR |
| `days_since_created` | Number of days since the record was created |
| `follow_up_required` | Boolean indicating whether follow-up is flagged |

The dataset covers five appointment categories:

- General Medicine
- Cardiology
- Dermatology
- Pediatrics
- Orthopedics

It includes the following appointment statuses:

- Scheduled
- Completed
- Cancelled
- No-Show
- Rescheduled

### Dataset observations

The generated dataset contains:

- Total records: 50
- Records requiring follow-up: 10
- Follow-up proportion: 20%
- Minimum `days_since_created`: 0
- Maximum `days_since_created`: 30
- Average `days_since_created`: 16.44

The follow-up flag occurs across multiple appointment statuses, including Completed, Cancelled, No-Show, Rescheduled, and Scheduled. Therefore, the flag and resulting score must be interpreted alongside the appointment status.

**Important:** All appointment records and associated fees are synthetic sample data. They do not represent actual Practo customer records or official Practo pricing.

## 3. Lookup Behavior

The tool exposes the following function:

`check_appointment_status(record_id: str) -> dict`

### Input handling

The function accepts an appointment record ID as a string.

Before searching:

1. It validates that the input is a non-empty string.
2. It removes leading and trailing whitespace.
3. It converts the record ID to uppercase.
4. It loads the appointment dataset.
5. It searches for a matching record ID.

This allows IDs with different casing or surrounding whitespace to be normalized before lookup.

### Successful lookup

When a matching appointment is found, the function returns:

- `found`: Indicates that the appointment was found.
- `record_id`: The matched appointment identifier.
- `status`: The current appointment status.
- `consultation_fee_inr`: The consultation fee.
- `escalation_score`: The calculated administrative prioritization score.

Example:

```python
{
    "found": True,
    "record_id": "APT-0001",
    "status": "Cancelled",
    "consultation_fee_inr": 500,
    "escalation_score": 0.0667
}
```

### Appointment not found

When no matching record exists, the function returns:

```python
{
    "found": False,
    "record_id": "UNKNOWN-ID",
    "error": "Appointment record not found."
}
```

Invalid input, missing dataset files, and malformed dataset structures raise appropriate exceptions rather than silently returning incorrect results.

## 4. Administrative Prioritization Score

The tool calculates an administrative prioritization score using two appointment attributes:

- Whether follow-up is required.
- How many days have passed since the appointment record was created.

The formula is:

\[
E = 0.6F + 0.4\left(\frac{D}{30}\right)
\]

Where:

- \(E\) = Administrative prioritization score.
- \(F\) = Follow-up indicator:
  - 1 if `follow_up_required` is `True`.
  - 0 if `follow_up_required` is `False`.
- \(D\) = `days_since_created`.
- 30 = Maximum age of a record in the generated dataset.

### Weight distribution

| Component | Weight | Interpretation |
|---|---:|---|
| Follow-up requirement | 60% | Gives greater importance to records explicitly flagged for follow-up |
| Record age | 40% | Increases the score as the record becomes older |
| Total | 100% | Produces a score between 0 and 1 |

### Rationale

The follow-up flag receives a higher weight because it explicitly identifies records requiring follow-up consideration.

Record age contributes to the score because older records may deserve additional administrative attention.

The 60/40 weighting is a design heuristic selected for this project. It is not statistically optimized or clinically validated.

The normalization factor of 30 is based on the generated dataset's `days_since_created` range of 0 to 30 days.

### Example calculation

Consider an appointment with:

- `follow_up_required = False`
- `days_since_created = 5`

Then:

\[
E = 0.6(0) + 0.4\left(\frac{5}{30}\right)
\]

\[
E = 0.0667
\]

The resulting score is approximately `0.0667`.

### Interpretation and limitations

The score is intended only as an administrative prioritization heuristic.

It must not be interpreted as:

- A measure of medical urgency.
- A clinical risk score.
- An indication of a patient's medical condition.
- A recommendation for diagnosis or treatment.
- Proof that an appointment requires intervention.

The appointment status must always be considered alongside the score. For example, a record marked as Completed may still have its follow-up flag set.

The score does not independently determine what action should be taken. It provides an additional administrative signal that can be presented to the support agent.

## 5. Error Handling and Data Integrity

The implementation includes validation for:

- Empty or whitespace-only record IDs.
- Non-string record IDs.
- Missing appointment dataset.
- Invalid JSON dataset structure.
- Non-boolean follow-up indicators.
- Non-integer record ages.
- Record ages outside the supported range of 0–30 days.

The lookup operation is read-only. It does not modify appointment records or update their statuses.

## 7. Limitations and Future Considerations

The current implementation is intentionally deterministic and uses a locally generated synthetic dataset.

Potential future improvements include:

- Supporting a database-backed appointment repository.
- Avoiding repeated dataset loading for larger datasets.
- Introducing configurable administrative prioritization weights.
- Adding audit logging for appointment lookup operations.

These improvements are outside the scope of the current lookup implementation.
